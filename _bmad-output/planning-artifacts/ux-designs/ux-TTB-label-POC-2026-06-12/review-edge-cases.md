# Edge-Case Audit — TTB Label Review UX Spine (EXPERIENCE.md + DESIGN.md)

> Method-driven walk of every branching path, boundary, and state in the experience.
> Reports ONLY unhandled edge cases — gaps where the spine does not say what happens.
> The spines were NOT modified. Audited 2026-06-12 against the State Patterns and Component Patterns tables.

## Overall verdict

The state coverage is strong on the *happy path and the most-anticipated failure surfaces* — empty queue, empty-type queue, soft/normalized diff, can't-verify, LLM-unreachable, and the open-REVIEW soft gate are all explicitly resolved, which is more than most spines at this stage. The gaps cluster in three predictable corners: (1) **boundary quantities** the panels claim to support but never specify behavior for (0 images, 10 images, mixed verdicts in the roll-up, zero/all-REVIEW checklists); (2) **post-commit and persistence** edges (undo a just-recorded disposition, double-submit, persistence failure, browser refresh vs. navigate-away); and (3) **demo/operational collisions** (reset while an item is open, concurrent specialists, cold-start with nothing ready, the Benchmark Report and token gate before/after their data exists). None are visual-identity gaps — DESIGN.md is appropriately scoped — they are behavioral states the EXPERIENCE.md State Patterns table doesn't yet enumerate.

## Unhandled edge cases

### Critical

**[critical] Verdict roll-up rule is never stated** — *Trigger:* a submission has mixed check results (e.g., some PASS, one FAIL, two REVIEW). *Why it matters:* the Suggested-verdict Alert ("Roll-up of all checks") and the chevron/checklist all depend on a submission-level verdict, but the spine never defines the precedence rule (any FAIL → FAIL? any REVIEW → REVIEW? what beats what?). Two engineers will implement it two different ways, and the wrong rule could suggest PASS on a submission containing a FAIL — directly undermining the P4 trust premise. *Resolution:* state the precedence explicitly — "submission verdict = FAIL if any check FAILs, else REVIEW if any check is REVIEW/can't-verify, else PASS" — in the Suggested-verdict Alert row.

**[critical] No undo / correct path after a disposition is recorded** — *Trigger:* specialist clicks Approve (or presses A) on the wrong item, or mis-types Notes, and the disposition persists + returns to Queue. *Why it matters:* the disposition is "the official, recorded act" with a timestamp; the navigation model is single-forward with "no back-stack browsing," so once recorded there is *no described route back to that submission at all*. A mis-click on a federal adjudication is unrecoverable in the current spine. *Resolution:* define behavior — either a brief post-record "Undo" affordance on return to Queue, or an explicit stated decision that disposition is final and irreversible in the POC (and surface that in microcopy so it's a known constraint, not a silent trap).

**[critical] Disposition persistence failure is undefined** — *Trigger:* the network/server call that persists "disposition + timestamp + Notes" fails (CPU-only server busy, transient error). *Why it matters:* the spine says "On record: persists disposition + timestamp, returns to Queue" as if it always succeeds. If it silently returns to Queue on failure, the specialist believes they adjudicated an item that was never recorded — a lost official act. "No work loss" is an explicit accessibility promise this violates. *Resolution:* add a State Pattern — on persist failure, stay on Review, keep Notes/ticks intact, show an honest retry affordance ("Couldn't save your decision — try again"); never return to Queue until the act is confirmed saved.

### High

**[high] Cold-start demo: nothing of ANY type is ready** — *Trigger:* fresh demo / just after reset, background pre-compute hasn't finished any item yet, so the queue has items but none are `ready`. *Why it matters:* "Empty queue" copy is "No submissions waiting right now" — but here submissions *exist*, they're just processing. The Item-not-ready state is described as "invisible to the specialist," which means the screen would show the empty-queue message even though work is arriving. An evaluator at cold start sees a misleadingly empty product. *Resolution:* distinguish "queue truly empty" from "items present but still processing" — e.g., "Submissions are being prepared — the next one will be ready shortly," not the empty-state copy.

**[high] Double-submit / double-click on a disposition** — *Trigger:* specialist double-clicks Approve, or presses A then clicks Approve before the screen transitions. *Why it matters:* could double-record the disposition or fire the action against the *next* served item. No debounce/disable-on-submit behavior is specified. On a recorded official act this is a data-integrity risk. *Resolution:* specify that disposition controls disable immediately on first activation until the record completes and the transition fires (idempotent submit).

**[high] Demo reset while a specialist has an item open** — *Trigger:* the operational "Demo reset (restore fixture queue, clear dispositions)" runs while a specialist is mid-review on an item that reset clears. *Why it matters:* the IA lists reset as a live operational route but never says what happens to an open Review session whose item was just reset out from under it. Recording a disposition afterward could target a stale/nonexistent item. The prompt flags this directly; the spine is silent. *Resolution:* state the behavior — either reset is blocked/deferred while a session is active, or the open Review shows a calm "This item was reset — returning to Queue" notice and discards the in-progress disposition.

**[high] Government Warning entirely absent from the label** — *Trigger:* the §16.21 warning text is not present anywhere on any image. *Why it matters:* the Gov-Warning card spec covers wording-deviation (character diff) and the bold/caps "couldn't verify" case, but not the *total-absence* case. Absent ≠ reworded; it's an unambiguous FAIL with different copy ("Required warning not found on label" vs. a diff). Conflating it with a diff or a "couldn't verify" would misstate a hard compliance failure. *Resolution:* add an explicit NOT_FOUND state to the Gov-Warning card — FAIL verdict, "Required Government Warning not found on the submitted images," distinct from the wording-diff layout.

**[high] Field NOT_FOUND vs. MISMATCH are not distinguished** — *Trigger:* an application field (e.g., ABV) is simply absent on the label, vs. present-but-different. *Why it matters:* the field card spec defines match / mismatch / soft only. NOT_FOUND (label is missing a required element) is a different finding from MISMATCH (label says something that disagrees), and they need different copy and possibly different verdicts. Rendering "absent" as a red character-diff against an empty string is confusing and misrepresents the defect. *Resolution:* add a NOT_FOUND field-card state ("Not found on label" with the OCR side empty and a plain note), separate from mismatch.

**[high] Tick-state persistence across a browser refresh (vs. navigate-away)** — *Trigger:* specialist refreshes the browser (or it reloads) mid-review. *Why it matters:* the spine promises tick-state "persists per submission across navigate-away" and "no work loss," but navigate-away (in-app) is a weaker guarantee than a full page reload. If ticks live only in client memory, a refresh wipes a human's judgment ticks and any Notes — violating the no-work-loss floor. *Resolution:* specify that tick-state and Notes survive a full reload (server- or storage-backed per submission), not just in-app navigation.

### Medium

**[medium] Image panel boundaries: 0 images and the 10-image max** — *Trigger:* a submission arrives with zero usable images, or with the full 10. *Why it matters:* the panel is specced "1–10 images" — the lower bound excludes 0, but a submission *can* arrive imageless or with all images failing to decode, and the panel never says what renders. At 10 images, paging/role-label behavior at the max is unspecified (does paging wrap? is there an overflow?). *Resolution:* define the 0-image state (honest "No images available for this submission" with checks degraded accordingly) and confirm the pager handles exactly 10 without overflow.

**[medium] Some images decode, others fail** — *Trigger:* image 2 of 5 fails to decode but the rest load. *Why it matters:* "Pipeline failure (unreadable image)" is handled at the *check* level, but the image *panel* spec doesn't say how a single bad face is shown among good ones (blank page? error placeholder? skipped silently?). Silently skipping breaks the role-label paging count. *Resolution:* show a per-image error placeholder in the pager ("This image couldn't be loaded") so the face count and role labels stay honest.

**[medium] Enhance toggle when no preprocessing was applied (clean photo)** — *Trigger:* a clean, straight, glare-free photo where local-OpenCV preprocessing produced no meaningful change. *Why it matters:* the Enhance toggle is specced to show preprocessed "alongside" the original, but on a clean image there's nothing to enhance. The prompt asks directly: hidden, disabled, or shown inert? Showing an identical "enhanced" image looks broken; a live toggle that does nothing erodes trust. *Resolution:* state the rule — e.g., Enhance is disabled (with helper "No enhancement needed — this image is already clean") when preprocessing is a no-op.

**[medium] Zero conditional checks → does chevron step ④ disappear cleanly?** — *Trigger:* a beverage type/submission triggers no conditional checks. *Why it matters:* the chevron spec says "Conditional step only appears when conditional checks are triggered," but the numbered model (①–⑤) implies stable numbering. If ④ vanishes, does ⑤ Decide renumber to ④, and do keyboard/scroll targets shift? Unspecified renumbering risks an off-by-one in the step map. *Resolution:* confirm the collapse behavior — either steps renumber cleanly (④ Decide) or the Decide step keeps a stable position; state which.

**[medium] Every check is REVIEW (no PASS, no FAIL)** — *Trigger:* an all-REVIEW submission (e.g., bad photo across the board, many can't-verify). *Why it matters:* the roll-up copy ("4 of 6 passed automatically; 2 need your review") and the "calm, only problems draw the eye" premise assume a minority of flags. An all-loud screen has nothing quiet to sink — the calm-by-default design inverts. The suggested verdict and Alert copy for "0 passed automatically" aren't specified. *Resolution:* define the all-REVIEW copy and confirm the layout degrades gracefully when nothing is quiet ("0 of 6 passed automatically — all items need your review").

**[medium] OCR returns empty or garbage for a field** — *Trigger:* OCR yields an empty string or non-text noise for a field that the application *does* populate. *Why it matters:* this is neither match, mismatch, soft, nor clearly NOT_FOUND — it's an OCR-confidence failure. The spine handles "can't verify" for font-size/spatial (inherently unmeasurable) but not "OCR failed to read a readable-by-human field." Rendering garbage as a mismatch diff would wrongly imply the *label* is wrong. *Resolution:* add an OCR-uncertain field state — "Couldn't read this field reliably from the photo — please verify by eye," REVIEW not FAIL.

**[medium] Filtered queue has ready items, but only of the non-selected type** — *Trigger:* filter set to Wine; the only ready items are Spirits. *Why it matters:* "Empty type queue" copy ("The wine queue is empty") is correct here — but the *adjacent* truth is that other work IS available under "Any." The copy hints "Try Any," which is good, but it doesn't say whether the stats strip reflects per-type readiness so the specialist knows Any would serve something. Borderline-handled; the gap is whether the specialist can tell *Any* is non-empty. *Resolution:* ensure the empty-type message / stats strip signals that other-type work is available ("Wine queue empty — 3 ready under Any").

**[medium] Application field itself is blank** — *Trigger:* the application (maker-submitted) value for a comparison field is empty, but the label shows text. *Why it matters:* the card stacks "application value above OCR value"; if the application side is blank, the comparison has no baseline to diff against. Unspecified whether this is a data-quality flag, a REVIEW, or a one-sided display. *Resolution:* define the blank-application state — show the OCR value with a note "No value submitted in the application for this field," REVIEW for human judgment.

### Low

**[low] Token expiry mid-session** — *Trigger:* the access token expires while the specialist is mid-review (or between Next Submission clicks). *Why it matters:* the token gate handles absent/invalid *at entry*, but not expiry *after* a session is underway. A mid-session bounce to the gate could lose unsaved Notes/ticks (no-work-loss conflict) or silently fail the next persist. *Resolution:* state mid-session expiry behavior — ideally tokens don't expire within a session, or expiry preserves in-progress work and re-prompts without data loss.

**[low] Help search with no results** — *Trigger:* specialist searches the local KB for a term with no match. *Why it matters:* the Help panel is "searchable" but no empty-results state is specified; a blank result list reads as broken. *Resolution:* add a calm no-results state ("No help articles matched — try a different term") consistent with the empty-queue voice.

**[low] Benchmark Report before any benchmark run has data** — *Trigger:* evaluator opens the Benchmark Report before any benchmark run has populated the comparison table. *Why it matters:* the table is specced read-only with rows/columns assuming data exists; an empty table undercuts the "we handed you buying data" climax of Flow 3. *Resolution:* add an empty/not-yet-run state for the Benchmark Report ("No benchmark runs yet" or seed it with the fixture run results).

**[low] Government Warning split across two images** — *Trigger:* the §16.21 warning text wraps across, e.g., the Back and Neck images. *Why it matters:* the Gov-Warning card compares a single on-label string to the regulation; if the warning spans faces, whether the engine concatenates across images or reads it as truncated-per-image is unspecified, risking a false FAIL on a compliant label. *Resolution:* state how multi-image warning text is assembled (or, if not assembled, surface it as "couldn't verify — warning spans multiple images").

**[low] A field with multiple OCR candidates across images** — *Trigger:* brand name appears on both the front (Brand) and back image, with slightly different OCR reads. *Why it matters:* the field card shows one OCR value; the spine doesn't say which candidate wins or whether disagreement across faces is surfaced. Picking the wrong face could manufacture a mismatch. *Resolution:* define candidate selection (e.g., best-confidence, or surface both with the source face) when a field is read on multiple images.

**[low] Concurrent specialists / multi-user not stated in the UX** — *Trigger:* two specialists both click Next Submission and could be served — or both pull — the same oldest-ready item. *Why it matters:* the PRD marks multi-user out of scope, but the EXPERIENCE.md never states this, so a reader could assume queue-locking exists. Silent on whether Next Submission reserves an item. *Resolution:* state the single-user POC assumption in the Queue/Next Submission behavior (or note Phase-2 queue-locking) so the absence of reservation is explicit, not an apparent bug.
