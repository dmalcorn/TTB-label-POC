# Story 1.3: Seed the fixture corpus with Ground Truth

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As an evaluator,
I want the database seeded with a realistic fixture corpus carrying Ground Truth,
so that the demo and the benchmark have reproducible data spanning all beverage types and verdict outcomes.

## Acceptance Criteria

**AC-1 — 30–50 submissions across all three types, spanning clean / violation / degraded**
**Given** `fixtures/` (synthetic label images + a Ground Truth CSV) and `app/db/seed.py`
**When** the seed script runs against an initialized database
**Then** 30–50 `submissions` are loaded spanning `DISTILLED_SPIRITS`, `WINE`, and `MALT_BEVERAGE`, including clean labels, every-Check-violation examples, and a degraded-image tail (glare, angle, curvature)
**And** each submission's `label_images` rows (1–10) are inserted with role/position/filename/metadata referencing real synthetic image files under `fixtures/`
**And** a `SEEDED` `audit_events` row is written per submission.

**AC-2 — Corpus composed for ≥1 of each verdict outcome per type**
**Given** the corpus design
**When** the engine later runs (Epic 3)
**Then** the seeded data is composed so that at least one submission per Engine Verdict outcome (`PASS` / `REVIEW` / `FAIL`) exists per beverage type — recorded as an `expected_verdict` design tag in the Ground Truth CSV (no engine runs in this story; this AC is satisfied by corpus composition + a coverage test over the CSV).

**AC-3 — Ground Truth per submission for accuracy scoring**
**Given** the Ground Truth CSV
**When** a submission is seeded
**Then** it carries Ground Truth on-label field values (what OCR should extract) for every matchable field, retained in `fixtures/ground_truth.csv` for the Epic-5 benchmark — distinct from the APPLICATION values stored on `submissions` (they match for clean cases and deliberately diverge for mismatch cases).

**AC-4 — Image-count constraint: 10 round-trips, 11th rejected**
**Given** the image constraints from `docs/image-handling.md` (1–10 images, tagged by role)
**When** a submission with 10 images is seeded
**Then** it round-trips correctly (all 10 readable through `repositories.list_label_images`)
**And** an attempt to attach an 11th image is rejected by validation (the seed layer raises, and the DB `CHECK (position BETWEEN 1 AND 10)` / `UNIQUE(submission_id, position)` enforce it).

**AC-5 — Synthetic only; data-dictionary coverage; reproducible & idempotent**
**Given** the no-registry-artwork and reproducibility constraints
**When** the corpus is inspected and the seed re-run
**Then** no COLA-registry-sourced artwork appears (all images synthetic, generated by the fixture generator)
**And** every seeded field resolves to an entry in `docs/data-dictionary.md`
**And** the seed is transactional and idempotent (a re-run restores the same corpus without duplicates — the reset-friendly basis Epic 6 builds `POST /reset` on).

*(Source: epics.md Story 1.3; FR-20; AR-12 (reset basis), AR-13; docs/database-schema.md §1.2/§1.7/§5; docs/image-handling.md §1/§2; docs/data-dictionary.md.)*

> **Scope note (binding):** This story adds **only** the `audit_events` table to `schema.sql` (the SEEDED event needs it). `submissions` + `label_images` already exist (Story 1.2). Do **NOT** create `ocr_results`/`llm_results`/`field_comparisons`/`checklist_items`/`review_progress`/`submission_extra_fields` — they belong to their owning stories.

## Dev Notes

### Scope guardrails (read first)
- **One new table only: `audit_events`.** Everything else (`ocr_results`, etc.) stays deferred. A 1.2 test already asserts the deep tables are absent — keep that true (update it to allow `audit_events`).
- **Ground Truth lives in the CSV, not the DB.** There is no `ground_truth` table in the schema; the Epic-5 benchmark reads `fixtures/ground_truth.csv`. The seed writes only APPLICATION values to `submissions`.
- **Seed is stdlib-only at runtime.** OpenCV is used **only** by the dev-time `fixtures/generate.py`; it is NOT added to `requirements.txt` or the Docker image in this story (it arrives with the Epic-2 pipeline). The committed JPEGs are what ship.

### The APPLICATION-vs-Ground-Truth distinction (do not conflate)
- `submissions.*` = the APPLICATION values (what the applicant filed). For a **clean** submission, the label (Ground Truth) matches these. For a **violation** submission, the on-label Ground Truth deliberately diverges (e.g. application `alcohol_content="45% Alc./Vol."` but label Ground Truth `40%`) so Epic 3's field-match FAILs and Epic 5 can score it.
- The image generator renders from the **Ground Truth (`gt_*`)** values (that's what's physically on the label). The seed stores the **APPLICATION** values on `submissions`. Both come from the one CSV row.
- Respect the **per-type ABV rule** (`data-dictionary.md §1` note): spirits always require ABV; ≤14% table wine does not; malt-beverage is conditional. Compose clean wine/beer rows that omit ABV without that being a violation — the corpus must not bake in false-FAILs (SM-C2 spirit).

### Authoritative sources — transcribe, don't invent
- `audit_events` DDL: `database-schema.md §1.7` (event_type vocabulary is fixed; `SEEDED` is the only one this story writes).
- Image model: `image-handling.md §1` (JPG/JPEG + TIFF, RGB, ≤750 KB, 1–10, one label per image; PNG is a documented TODO — do NOT use PNG) and `§2` (role tags `BRAND/BACK/NECK/STRIP/OTHER`, no `FRONT`). Generate `image/jpeg` RGB.
- Field semantics + `field_key` resolution: `data-dictionary.md §1` (every seeded field must appear there).
- Seeded-vs-computed split: `database-schema.md §5` — seed writes `submissions` APPLICATION fields + `status='RECEIVED'`, `label_images`, and one `SEEDED` audit_event. It does NOT write `engine_verdict`/`disposition`/`processing_ms` (those are computed later).

### Architecture compliance (must-follow)
- **snake_case** across CSV headers ↔ DB columns ↔ Python (the `gt_*`/design columns are CSV-only and clearly prefixed).
- **`db/` is the only SQL owner** — `seed.py` lives in `app/db/`, so its SQL is in-boundary. No SQL elsewhere.
- **No engine/verdict logic here** — `expected_verdict` is a design tag, never computed; the seed never sets `engine_verdict` or maps anything to a disposition (contract #4 intact).
- **Firewall:** generation and seeding are 100% local, zero egress. (Generation isn't even in the deployed image.)
- **5s read path** untouched — seeding is an offline/bootstrap operation, not a request path.
