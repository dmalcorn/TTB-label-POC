## Deferred from: code review of 3-1-normalization-and-verdict-roll-up-contracts (2026-06-13)

- **`normalize`/`parse_numeric` disagree on a unitless numeric value (`"45"`).** For `alcohol_content`/`net_contents`, `normalize("45", …)` falls back to the text pipeline and returns `"45"` (a plain-text comparison) while `parse_numeric("45", …)` returns `(None, None)` (unparseable, because no unit is adjacent). A label literally filed as `45` with no `%`/unit therefore bypasses the numeric tolerance band in Story 3.3 and compares as opaque text. Settle the single intended behavior (assume a unit, or reject both ways) in **Story 3.3** where the tolerance bands consume `parse_numeric` and the right default is observable. [app/normalize.py:normalize / parse_numeric]
- **Negative magnitudes accepted as a valid canonical value.** `parse_numeric("-5%", "alcohol_content")` → `(Decimal("-5"), "%")`; a physically impossible negative ABV/volume normalizes cleanly with no range guard. Validation/range checking is explicitly Story 3.3 scope (tolerance bands); add the non-negativity guard there, not in the pure contract. [app/normalize.py:_NUMBER]
- **Non-metric / unsupported net-contents units (`pint`, `fl oz`, `gallon`) silently fall back to raw text.** `_UNIT_PATTERNS` knows only `% proof ml l`; a US-customary filing degrades to an opaque text comparison rather than a parsed `(number, unit)`. Acceptable for the metric-standard-of-fill seeded corpus (27 CFR 5.203/4.72); revisit if real imported/customary filings land. [app/normalize.py:_UNIT_PATTERNS]
- **`v_field_comparisons` uses `CREATE VIEW IF NOT EXISTS` — a future change to the view's derivation logic is NOT re-applied on `init_db` against an existing DB.** This matches the project's established idempotence pattern for every schema object and the DDL is verbatim from `database-schema.md` §1.5, so it is correct today; flagged only because a view (unlike a table-add via the column ledger) has no migration path. If the `extracted_source` derivation ever changes, add a `DROP VIEW IF EXISTS` + recreate or a migration step. [app/db/schema.sql:v_field_comparisons]
- **Schema permits a `MATCH`/`MISMATCH` row whose source FK was nulled by `ON DELETE SET NULL`.** Deleting the referenced `ocr_results`/`llm_results` row nulls `source_*_id` (so the view's `extracted_source` → NULL) while `match_status` still reads `MATCH` — an inconsistent state with no CHECK/trigger tying the two. DDL is verbatim per §1.5 (spine wins); Story 3.1 does not write these rows. Revisit a consistency guard when the writers (3.2/3.3) and any delete path exist. [app/db/schema.sql:field_comparisons]

## Deferred from: code review of 2-3-local-opencv-image-preprocessing (2026-06-13)

- **Variant filename uniqueness relies on unique source basenames** — variants are named `{Path(src).stem}__enhanced.png`/`__binarized.png`. Safe for the seeded corpus (stems are `<ttb_id>_<NN>_<ROLE>`, globally unique), but two `label_images` sharing a stem (a future upload, or `a.jpg`+`a.png` in one submission) would overwrite each other and both DB rows would point at one file. Add a `label_image.id` qualifier to the variant name when duplicate/untrusted filenames become possible. [app/pipeline/preprocess.py:preprocess_image]
- **Glare detector misses flat (gradient-free) glare** — `normalize_illumination_glare` gates on background luma **spread**, so a uniformly blown-out hotspot with no surrounding gradient is a no-op (the inpaint branch is nested inside the spread gate). Deliberate tradeoff to avoid false-firing on plain white labels (Debug Log). Revisit tuning against real phone photos. [app/pipeline/preprocess.py:normalize_illumination_glare]
- **Orientation not normalized (EXIF + >45° skew)** — `IMREAD_COLOR` ignores EXIF orientation and `_detect_skew_angle` folds any angle into (-45, 45], so a 90°/180° rotated photo is never straightened and a ~45° skew flips correction direction at the fold boundary. The seeded fixtures are upright; this bites real uploaded phone photos. Add EXIF-orientation handling + a >45° branch when real uploads land. [app/pipeline/preprocess.py:decode_normalize_color / _detect_skew_angle]
- **Enhanced variant is grayscale, not color** — AC2/image-handling §3 frame the PaddleOCR-targeted enhanced variant as "grayscale/color"; PaddleOCR/PP-OCRv5 often prefer color. Defensible POC choice (the chain works on intensity); reconsider emitting a color enhanced variant when Story 2.4 wires PaddleOCR and can measure the accuracy delta. [app/pipeline/preprocess.py:preprocess_image]
- **Path robustness for untrusted inputs** — `SOURCE_IMAGES_DIR / image.filename` is not containment-checked (a `../`/absolute `filename` would escape the read-only fixture root), and stored variant paths are basenames relative to `generated_images_dir` with no record of which root they belong to (fragile if the config changes between the preprocess and OCR runs). Both are safe today (trusted seeded basenames + stable config); sanitize the source path and pin the resolution base when real uploads land. [app/pipeline/preprocess.py:preprocess_stage]

## Deferred from: code review of 2-2-background-sweep-and-submission-lifecycle (2026-06-12)

- **No per-job timeout — a hung stage wedges the whole pipeline** — `sweep` does `future.result()` with no timeout, and `job_defaults={'max_instances':1,'coalesce':True}` means while one tick is blocked on a hung worker, no further sweeps fire. Not triggerable by 2.2's passthrough stage, but the seam is explicitly designed for heavy native stages (Tesseract/Paddle/LLM) to plug in with zero scheduler changes — those stages can hang. Add a per-job timeout / hang-containment (and revisit the `shutdown(wait=True)` interaction) in the OCR (2.4) / LLM (2.5) stage stories. [app/pipeline/scheduler.py:sweep]
- **Audit-timeline ordering depends on a test-only tiebreak** — `audit_events.occurred_at` is `CURRENT_TIMESTAMP` (1-second resolution); a fast submission emits all four events in the same wall-clock second, so correct order needs `ORDER BY occurred_at, id`. That `, id` tiebreak currently lives only in the test `_events` helper. No production audit-timeline reader exists yet, but the review-workspace timeline UI story MUST order by `(occurred_at, id)` or events render out of order. [app/db/schema.sql / future timeline reader]
- **`actor` string diverges from the schema-doc convention** — pipeline writes `actor="pipeline"`; `database-schema.md` §1.7 documents per-job actors `system:ocr_job` / `system:analysis_job`. Schema-legal (free-text TEXT, no CHECK) and AC2's "with actor" is satisfied, but audit-trail provenance consistency matters for the procurement/evaluator story. 2.4/2.5 should emit the documented per-job actor names. [app/pipeline/status.py:PIPELINE_ACTOR]
- **`advance` permits multi-step forward jumps** — the guard only requires the target be strictly later in `FORWARD_STATUSES`, so e.g. `PROCESSING→DECIDED` would pass while skipping `READY_FOR_REVIEW`/`IN_REVIEW` and their audit rows. Not exercised in 2.2 (only `→READY_FOR_REVIEW` is called), but future lifecycle stories must not skip intermediate transitions; consider a single-step assertion in `advance`. [app/pipeline/status.py:advance]
- **AC1 atomicity test is serial, not concurrent** — `test_claim_is_atomic_only_one_winner` runs the two `claim_for_processing` calls sequentially on one thread, proving the conditional-`WHERE` guard but not a true concurrent race (the underlying atomic `UPDATE` is correct regardless). Strengthen with a genuine two-thread race on a file-backed WAL DB if a higher-fidelity proof is wanted. [tests/test_pipeline.py:test_claim_is_atomic_only_one_winner]

## Deferred from: code review of 2-1-engine-agnostic-ocr-llm-adapter-contracts (2026-06-12)

- **`word_boxes` JSON serialization is fragile to non-plain types** — `insert_ocr_result` does `json.dumps(result.word_boxes)` with no `default=`/coercion. `word_boxes` is typed `list[dict]`, but a real PaddleOCR engine (Story 2.4) commonly returns numpy scalars in box coords, which raise `TypeError: not JSON serializable` mid-insert. The contract requires plain in-memory types, so the fix belongs in the OCR adapters (Story 2.4): coerce boxes to plain `int`/`float` before constructing `OcrResult`. Add an adapter test with a numpy-bearing box. [app/db/repositories.py / Story 2.4 adapters]
- **`llm_results.label_image_id ON DELETE SET NULL` path untested** — `submission_id` is `ON DELETE CASCADE` and a benchmark-only LLM row already has `label_image_id=NULL`, so the SET-NULL transition only fires when a label image is deleted out from under a non-benchmark LLM row — never exercised. Add a deletion test if/when label-image deletion becomes a real path. [tests/test_adapters.py]
- **Partial-batch durability of the multi-engine write** — `connect()` commits only *after* the `with` body (post-yield), so a pipeline that inserts one engine's OCR row then raises before finishing the unit loses the earlier row on close (all-or-nothing). That atomic behavior is defensible, but whether per-engine partial progress should survive is an Epic-2 pipeline transaction-granularity decision. Settle it in the scheduler/lifecycle story (2.2). [app/db/connection.py]
